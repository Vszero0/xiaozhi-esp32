## 一、单例模式（Singleton Pattern）
### 1. 核心作用
保证一个类**在整个程序生命周期内有且仅有一个实例**，并提供一个全局唯一的访问入口。

### 2. 典型应用场景
- 全局日志管理器：所有模块共用一个日志实例，避免重复打开文件、日志顺序混乱
- 系统配置管理器：全局唯一的配置读取入口，避免重复加载配置文件
- 数据库连接池：统一管理连接资源，避免重复创建连接

### 3. C++代码实现（Meyers单例，线程安全）
C++11 之后推荐使用**局部静态变量**实现懒汉单例，编译器保证静态变量初始化的线程安全性，是最简洁安全的写法。

```cpp
#include <iostream>
#include <string>
using namespace std;

class Logger {
public:
    // 全局唯一访问入口
    static Logger& getInstance() {
        // 局部静态变量：第一次调用时才初始化，C++11保证线程安全
        static Logger instance;
        return instance;
    }

    // 禁用拷贝构造、赋值运算符，防止实例被复制
    Logger(const Logger&) = delete;
    Logger& operator=(const Logger&) = delete;
    // 禁用移动构造
    Logger(Logger&&) = delete;

    // 业务方法：输出日志
    void info(const string& msg) {
        cout << "[INFO] " << msg << endl;
    }

private:
    // 构造函数私有，外部无法直接创建对象
    Logger() {
        cout << "日志管理器初始化（全局仅执行1次）" << endl;
    }
    // 析构函数私有，外部无法销毁
    ~Logger() = default;
};

int main() {
    // 全局通过getInstance访问，两次获取的是同一个实例
    Logger::getInstance().info("程序启动");
    Logger::getInstance().info("业务逻辑执行中");
    return 0;
}
```

### 4. 模式价值
- **资源统一管控**：避免重复创建/销毁资源，减少性能开销
- **全局访问便捷**：无需在模块间层层传递对象指针
- **注意事项**：单例全局状态会增加模块耦合，滥用会导致代码难以测试；多线程场景下必须保证初始化线程安全。

## 二、工厂模式（Factory Pattern）
工厂模式是一类“封装对象创建逻辑”的模式，工程中最常用的是**工厂方法模式**（23种经典设计模式之一），它解决了简单工厂违反开闭原则的问题。

### 1. 核心作用
将**对象的创建与使用解耦**，客户端只依赖抽象接口，不关心具体对象的创建细节；新增产品时无需修改原有代码，符合开闭原则。

### 2. 典型应用场景
- 游戏开发：怪物生成器，根据关卡动态创建普通怪、精英怪、Boss
- 支付系统：对接多种支付渠道（微信、支付宝、银行卡），灵活切换支付方式
- 跨平台渲染：创建不同平台的渲染器（OpenGL、Vulkan、DirectX）

### 3. C++代码实现（工厂方法模式）
以游戏怪物生成为例：
```cpp
#include <iostream>
#include <memory>
using namespace std;

// -------------------------- 抽象产品 --------------------------
class Monster {
public:
    virtual ~Monster() = default; // 基类必须有虚析构函数
    virtual void attack() = 0;    // 怪物攻击行为
};

// -------------------------- 具体产品 --------------------------
// 普通小怪
class NormalMonster : public Monster {
public:
    void attack() override {
        cout << "普通怪物攻击，造成10点伤害" << endl;
    }
};

// 精英怪物
class EliteMonster : public Monster {
public:
    void attack() override {
        cout << "精英怪物攻击，造成35点伤害" << endl;
    }
};

// Boss怪物
class BossMonster : public Monster {
public:
    void attack() override {
        cout << "Boss释放技能，造成100点伤害" << endl;
    }
};

// -------------------------- 抽象工厂 --------------------------
class MonsterFactory {
public:
    virtual ~MonsterFactory() = default;
    virtual unique_ptr<Monster> createMonster() = 0; // 工厂方法
};

// -------------------------- 具体工厂 --------------------------
// 普通怪工厂
class NormalMonsterFactory : public MonsterFactory {
public:
    unique_ptr<Monster> createMonster() override {
        return make_unique<NormalMonster>();
    }
};

// 精英怪工厂
class EliteMonsterFactory : public MonsterFactory {
public:
    unique_ptr<Monster> createMonster() override {
        return make_unique<EliteMonster>();
    }
};

// Boss工厂
class BossMonsterFactory : public MonsterFactory {
public:
    unique_ptr<Monster> createMonster() override {
        return make_unique<BossMonster>();
    }
};

int main() {
    // 客户端只依赖抽象工厂和抽象产品
    unique_ptr<MonsterFactory> factory = make_unique<EliteMonsterFactory>();
    auto monster = factory->createMonster();
    monster->attack();

    // 切换工厂即可切换产品，无需修改业务逻辑
    factory = make_unique<BossMonsterFactory>();
    monster = factory->createMonster();
    monster->attack();
    return 0;
}
```

### 4. 模式价值
- **解耦创建与使用**：客户端不需要知道具体类名，只需要知道对应的工厂
- **符合开闭原则**：新增怪物类型时，只需要加新产品类+新工厂类，不用修改原有代码
- **对比简单工厂**：简单工厂用一个工厂类+switch创建所有产品，新增产品必须修改工厂代码，违反开闭原则；工厂方法是每个产品对应一个工厂，扩展性更强。

## 三、状态模式（State Pattern / 状态机模式）
### 1. 核心作用
允许对象在**内部状态改变时改变自身行为**，看起来就像修改了类本身。将状态判断逻辑分散到各个状态类中，消除庞大的`if-else/switch`分支。

### 2. 典型应用场景
- 电梯控制系统：开门、关门、运行、停止，不同状态下操作的行为不同
- 游戏角色状态机：待机、奔跑、跳跃、攻击、死亡，状态间有严格的切换规则
- 订单状态流转：待支付、已支付、发货中、已完成、已退款

### 3. C++代码实现（电梯状态机）
```cpp
#include <iostream>
#include <memory>
using namespace std;

// 前置声明上下文类
class LiftContext;

// -------------------------- 抽象状态类 --------------------------
class LiftState {
protected:
    LiftContext* context; // 持有上下文指针，用于切换状态
public:
    virtual ~LiftState() = default;
    void setContext(LiftContext* ctx) { context = ctx; }

    // 四个操作：开门、关门、运行、停止
    virtual void openDoor() = 0;
    virtual void closeDoor() = 0;
    virtual void run() = 0;
    virtual void stop() = 0;
};

// -------------------------- 上下文类（电梯） --------------------------
class LiftContext {
private:
    unique_ptr<LiftState> currentState;
public:
    // 切换状态
    void setState(unique_ptr<LiftState> state) {
        currentState = move(state);
        currentState->setContext(this);
    }

    // 对外暴露的操作接口，实际委托给当前状态处理
    void openDoor()  { currentState->openDoor(); }
    void closeDoor() { currentState->closeDoor(); }
    void run()       { currentState->run(); }
    void stop()      { currentState->stop(); }
};

// -------------------------- 具体状态类 --------------------------
// 开门状态
class OpenState : public LiftState {
public:
    void openDoor() override {
        cout << "[状态-开门] 门已经打开，无需重复操作" << endl;
    }
    void closeDoor() override {
        cout << "[状态-开门] 执行关门..." << endl;
        context->setState(make_unique<class CloseState>());
    }
    void run() override {
        cout << "[状态-开门] 门未关闭，无法运行电梯！" << endl;
    }
    void stop() override {
        cout << "[状态-开门] 电梯已处于停止状态" << endl;
    }
};

// 关门状态
class CloseState : public LiftState {
public:
    void openDoor() override {
        cout << "[状态-关门] 执行开门..." << endl;
        context->setState(make_unique<OpenState>());
    }
    void closeDoor() override {
        cout << "[状态-关门] 门已经关闭" << endl;
    }
    void run() override {
        cout << "[状态-关门] 电梯开始运行..." << endl;
        context->setState(make_unique<class RunState>());
    }
    void stop() override {
        cout << "[状态-关门] 电梯已停止" << endl;
    }
};

// 运行状态
class RunState : public LiftState {
public:
    void openDoor() override {
        cout << "[状态-运行] 电梯高速运行中，禁止开门！" << endl;
    }
    void closeDoor() override {
        cout << "[状态-运行] 门已保持关闭" << endl;
    }
    void run() override {
        cout << "[状态-运行] 电梯正在运行中" << endl;
    }
    void stop() override {
        cout << "[状态-运行] 电梯减速停止..." << endl;
        context->setState(make_unique<class StopState>());
    }
};

// 停止状态
class StopState : public LiftState {
public:
    void openDoor() override {
        cout << "[状态-停止] 执行开门..." << endl;
        context->setState(make_unique<OpenState>());
    }
    void closeDoor() override {
        cout << "[状态-停止] 执行关门..." << endl;
        context->setState(make_unique<CloseState>());
    }
    void run() override {
        cout << "[状态-停止] 电梯开始运行..." << endl;
        context->setState(make_unique<RunState>());
    }
    void stop() override {
        cout << "[状态-停止] 电梯已处于停止状态" << endl;
    }
};

int main() {
    LiftContext lift;
    lift.setState(make_unique<StopState>()); // 初始状态：停止

    lift.openDoor();   // 停止→开门
    lift.run();        // 开门状态不能运行
    lift.closeDoor();  // 开门→关门
    lift.run();        // 关门→运行
    lift.openDoor();   // 运行状态不能开门
    lift.stop();       // 运行→停止
    return 0;
}
```

### 4. 模式价值
- **消除分支爆炸**：避免用几十个`if-else`判断当前状态，代码可读性和可维护性大幅提升
- **状态流转清晰**：每个状态的行为和切换逻辑内聚在一个类中，符合单一职责原则
- **扩展性强**：新增状态只需要加新的状态类，无需修改原有状态和上下文代码

## 四、策略模式（Strategy Pattern）
### 1. 核心作用
封装一系列可互相替换的算法/行为，让算法独立于使用它的客户端变化。运行时可以动态切换算法，无需修改业务代码。

### 2. 典型应用场景
- 商城促销系统：无折扣、满减、折扣券、拼团价等多种价格计算策略
- 排序算法：根据数据规模切换冒泡、快排、归并排序
- 路径规划：驾车、步行、公交等不同路线计算策略

### 3. C++代码实现（商城价格计算）
```cpp
#include <iostream>
#include <memory>
using namespace std;

// -------------------------- 抽象策略类 --------------------------
class DiscountStrategy {
public:
    virtual ~DiscountStrategy() = default;
    // 计算最终价格
    virtual double calcFinalPrice(double originalPrice) = 0;
};

// -------------------------- 具体策略类 --------------------------
// 策略1：无折扣
class NoDiscount : public DiscountStrategy {
public:
    double calcFinalPrice(double originalPrice) override {
        return originalPrice;
    }
};

// 策略2：满减策略（满threshold减discount）
class FullReduction : public DiscountStrategy {
private:
    double threshold; // 满减门槛
    double discount;  // 减免金额
public:
    FullReduction(double th, double dis) : threshold(th), discount(dis) {}

    double calcFinalPrice(double originalPrice) override {
        return originalPrice >= threshold ? originalPrice - discount : originalPrice;
    }
};

// 策略3：折扣券策略（按比例打折）
class CouponDiscount : public DiscountStrategy {
private:
    double rate; // 折扣比例，0.8代表8折
public:
    CouponDiscount(double r) : rate(r) {}

    double calcFinalPrice(double originalPrice) override {
        return originalPrice * rate;
    }
};

// -------------------------- 上下文类 --------------------------
class PriceCalculator {
private:
    unique_ptr<DiscountStrategy> strategy;
public:
    // 运行时动态设置/切换策略
    void setStrategy(unique_ptr<DiscountStrategy> s) {
        strategy = move(s);
    }

    // 业务方法：计算价格，实际委托给策略执行
    double getPrice(double originalPrice) {
        if (!strategy) return originalPrice;
        return strategy->calcFinalPrice(originalPrice);
    }
};

int main() {
    PriceCalculator calculator;
    double goodsPrice = 299.0;

    // 无折扣
    calculator.setStrategy(make_unique<NoDiscount>());
    cout << "原价：" << calculator.getPrice(goodsPrice) << endl;

    // 满200减50
    calculator.setStrategy(make_unique<FullReduction>(200, 50));
    cout << "满减后：" << calculator.getPrice(goodsPrice) << endl;

    // 75折券
    calculator.setStrategy(make_unique<CouponDiscount>(0.75));
    cout << "折扣后：" << calculator.getPrice(goodsPrice) << endl;
    return 0;
}
```

### 4. 模式价值
- **算法自由切换**：运行时动态更换策略，灵活性极强
- **消除条件分支**：避免用`if-else`堆叠各种算法逻辑
- **符合开闭原则**：新增折扣策略只需要加新类，无需修改价格计算器和原有业务代码

## 四种模式核心区别总结
| 模式     | 核心目的       | 解决的问题                       |
| -------- | -------------- | -------------------------------- |
| 单例模式 | 保证实例唯一   | 全局资源重复创建、状态不一致     |
| 工厂模式 | 封装对象创建   | 对象创建与使用耦合、扩展困难     |
| 状态模式 | 状态驱动行为   | 大量状态判断分支、状态流转混乱   |
| 策略模式 | 封装可替换算法 | 算法逻辑堆叠、运行时无法灵活切换 |

### 1. `#include` 头文件 与 `using namespace` 的区别
很多初学者会混淆二者，它们是完全不同层面的语法：
- **`#include <iostream>` 是预处理指令**
  它的本质是**文本级代码引入**：程序编译前，预处理器会把`iostream`标准头文件里的所有代码，原封不动地粘贴到`#include`所在的位置。
  `iostream`里定义了`cout`、`cin`等输入输出工具的声明。没有这行，编译器根本不认识`cout`、`cin`是什么。
  简单理解：`#include`是「把工具的代码真正拿进你的程序里」。

- **`using namespace std;` 是命名空间声明**
  C++标准库的所有组件，都被放在`std`这个命名空间里，目的是避免命名冲突（比如你自己写了一个叫`cout`的函数，不会和标准库重名冲突）。
  不写`using namespace std;`的话，你必须写全称：`std::cout`、`std::cin`。
  它的作用只是**简化书写**：告诉编译器“后续代码里，std命名空间里的名字可以直接用，不用每次加`std::`前缀”。
  简单理解：`using namespace`只是「给工具名起简称」，并不会引入新代码。

⚠️ 注意：不存在“using的库”这种说法，库的引入永远靠`#include`，using只负责简化命名。

---

### 2. `static Logger& getInstance()` 中的 `&`
这里的`&`表示**函数返回值是引用类型**，即`Logger&`是「Logger类型的引用」。

#### 什么是引用？
引用可以理解为**对象的“别名”**，它和原对象指向同一块内存地址。操作引用就是操作原对象本身，**不会产生任何拷贝**。

#### 单例里为什么必须返回引用？
单例的核心要求是「全局有且仅有一个实例」。
- 如果写成`static Logger getInstance()`（返回值，不带&），调用时会把内部的唯一实例**拷贝出一个新对象**返回，程序里就会出现多个Logger实例，直接破坏单例规则。
- 返回引用`Logger&`，返回的就是内部那个唯一实例本身，没有拷贝，保证全局只有一个实例。

补充：前面的`static`表示这是**类的静态成员函数**——它属于整个类，不属于某个具体对象，所以调用时要用`类名::函数名`。

---

### 3. 类里的 `public` / `private` 访问限定符
C++的`class`可以通过访问限定符，控制类的成员（变量、函数）在类外部能不能被访问，这是面向对象「封装」特性的核心手段。一共三种：

| 限定符      | 访问权限                               | 对应示例场景                                       |
| ----------- | -------------------------------------- | -------------------------------------------------- |
| `public`    | 类内部、类外部都可以自由访问           | 对外暴露的接口，比如`getInstance()`、`info()`      |
| `private`   | 只有类内部可以访问，类外部完全无法触碰 | 内部数据、不想被外部修改的逻辑，比如单例的构造函数 |
| `protected` | 类内部和派生类可以访问，外部不行       | 继承场景下给子类暴露的成员                         |

#### 结合单例代码理解：
```cpp
class Logger {
public:
    static Logger& getInstance(); // 公有：给外部调用的唯一入口
    void info(string msg);        // 公有：对外的业务功能
private:
    Logger();  // 私有：外部不能new对象，从根源保证单例
    ~Logger(); // 私有：外部不能随意销毁实例
};
```
把构造函数设为`private`，外部就无法写`Logger log;`创建新对象，只能通过`getInstance()`获取唯一实例，这就是封装的作用。

💡 小规则：`class`默认的访问权限是`private`，`struct`默认是`public`。

### 4. 构造函数与析构函数（`~`）
这两个是类的特殊成员函数，分别负责对象的「初始化出生」和「销毁清理」，由编译器自动调用，不需要手动调用。

#### 构造函数
- 名字**和类名完全相同**，没有返回值（连`void`都不用写）。
- 对象被创建时（定义局部变量、`new`对象时）自动执行，用来做初始化工作（打开文件、分配内存、赋初值等）。
- 支持重载，可以传不同参数创建对象。

示例里的`Logger()`就是构造函数，单例场景下把它设为`private`，就是禁止外部创建对象。

#### 析构函数
- 名字是`~类名`，比如`~Logger()`，没有参数、没有返回值，不能重载。
- 对象被销毁时（局部变量离开作用域、`delete`指针时）自动执行，用来做资源清理（关闭文件、释放内存、断开连接等）。
- 符号`~`是析构函数的固定标识，读作“波浪号”。

示例里的`virtual ~Monster() = default;`，其中`=default`表示让编译器自动生成默认的空实现，不用手动写函数体。

---

### 5. `::` 作用域解析运算符
`::`叫**作用域解析运算符**，用来指明「这个成员属于哪个作用域」，主要有两种用法：

1. **访问类的静态成员**
   静态成员（static函数、static变量）属于整个类，不属于某个具体对象，因此不能用`.`或`->`访问，必须用`类名::成员名`。
   比如`Logger::getInstance()`，就是调用Logger类里的静态函数`getInstance`。

2. **访问命名空间里的成员**
   比如`std::cout`，就是访问`std`命名空间里的`cout`对象。写了`using namespace std;`之后可以省略前缀，本质还是通过命名空间找到的。

#### 和 `.`、`->` 的区别
- `.`：普通对象访问成员，比如`log.info("xxx")`
- `->`：指针（包括智能指针）访问成员，比如`factory->createMonster()`
- `::`：类/命名空间访问静态成员，或访问全局作用域

---

### 6. `class NormalMonster : public Monster` 类继承
这是C++面向对象「继承」的标准语法：
```
派生类名 : 继承方式 基类名
```
- `Monster`是**基类（父类）**，定义了所有怪物通用的接口和属性
- `NormalMonster`是**派生类（子类）**，自动拥有基类的所有成员，还可以扩展自己的功能、重写基类的虚函数

#### 继承方式
最常用的是**`public`公有继承**：
- 基类的`public`成员，在派生类中依然是`public`
- 基类的`protected`成员，在派生类中依然是`protected`
- 基类的`private`成员，派生类不能直接访问

公有继承表达「is-a（是一种）」的关系：普通怪物是一种怪物，Boss也是一种怪物。因此可以用`Monster*`基类指针统一管理所有子类对象，调用虚函数时自动执行对应子类的逻辑，这就是**多态**。

---

### 7. 为什么基类必须有虚析构函数？
这是C++多态场景下的硬性规则：**只要你用基类指针/引用管理派生类对象，基类的析构函数就必须是`virtual`虚函数**。

#### 背后原因
当你写这样的代码：
```cpp
unique_ptr<Monster> m = make_unique<NormalMonster>();
// 对象生命周期结束时，智能指针会自动delete内部指针
```
这里基类指针指向了派生类对象。如果基类析构**不是虚函数**：
- `delete`时，编译器只会调用基类`Monster`的析构函数
- 派生类`NormalMonster`的析构函数完全不会执行
- 如果派生类里申请了内存、打开了文件，就会造成**内存泄漏、资源泄漏**

如果基类析构是**虚函数**：
- `delete`时会根据对象的实际类型，先调用派生类析构，再调用基类析构
- 所有资源都会被完整释放

因此示例里写了`virtual ~Monster() = default;`，这是多态基类的标准写法。

---

### 8. `unique_ptr<Monster>` 中的泛型（模板）
`<>`语法是C++的**模板（Template）**，也就是泛型编程。

#### 什么是模板？
你可以把模板理解成「代码生成模具」：给它传入一个具体类型，它就自动生成对应类型的代码。
- `unique_ptr`是标准库提供的**类模板**，它本身不是一个具体的类，而是生成类的模具
- `<Monster>`是传入的**模板实参**，告诉编译器：我要一个专门管理`Monster`类型的智能指针
- 编译器会自动生成一份适配`Monster`类型的`unique_ptr`代码

同理，`vector<int>`、`string`本质都是模板的应用。模板的核心价值是**类型参数化**：一份模板代码可以适配无数种类型，不用重复写逻辑。

---

### 9. `return make_unique<NormalMonster>();` 直接返回函数
分两层理解：

#### 第一层：`make_unique`是什么
`make_unique`是C++标准库的**函数模板**，作用是**安全、简洁地创建一个`unique_ptr`智能指针对象**。
`make_unique<NormalMonster>()`会做两件事：
1. 在堆内存上创建一个`NormalMonster`对象
2. 把它包装成`unique_ptr<NormalMonster>`类型的智能指针并返回

#### 第二层：为什么能返回给`unique_ptr<Monster>`
函数声明的返回值是`unique_ptr<Monster>`，但我们返回的是`unique_ptr<NormalMonster>`，这是C++的**向上转型**规则：
- 派生类指针可以隐式转换成基类指针（因为NormalMonster本质上是一种Monster）
- 智能指针也支持这种转换：`unique_ptr<NormalMonster>`可以自动转成`unique_ptr<Monster>`

另外，直接返回临时对象时，编译器会做**返回值优化（RVO）**，不会产生多余的拷贝，效率很高。

---

### 10. `auto` 关键字 和 `->` 运算符
#### `auto` 关键字（C++11引入）
`auto`是**自动类型推导**：编译器会根据等号右边表达式的类型，自动推导出左边变量的类型，不用手动写长长的类型名。

示例里：
```cpp
auto monster = factory->createMonster();
```
`createMonster()`的返回值是`unique_ptr<Monster>`，所以编译器自动推导出`monster`就是这个类型，和你手动写完全等价。

它的好处是：
- 简化代码，尤其是类型很长的时候（比如迭代器、复杂模板类型）
- 避免手动写错类型
- 后续类型变化时不用改变量声明

#### `->` 箭头运算符
`->`是**指针访问成员运算符**，用来通过指针（包括智能指针）访问对象的成员函数/变量。

示例里`factory`是`unique_ptr<MonsterFactory>`类型，本质是个指针，所以调用成员函数要用`->`：
```cpp
factory->createMonster();
```
它完全等价于：
```cpp
(*factory).createMonster();
```
`->`就是语法糖，写起来更简洁。规则总结：普通对象用`.`，指针用`->`。

### 第二步：代码逐行解析

#### 1. 回调结构体定义（在 audio_service.h 中）

```cpp
// audio_service.h:78-83
struct AudioServiceCallbacks {
    // 无参数回调：发送队列有数据时调用
    std::function<void(void)> on_send_queue_available;
    
    // 带参数回调：检测到唤醒词时调用，参数是唤醒词字符串
    std::function<void(const std::string&)> on_wake_word_detected;
    
    // 带参数回调：语音活动检测状态变化时调用，参数是是否在说话
    std::function<void(bool)> on_vad_change;
    
    // 无参数回调：音频测试队列满时调用
    std::function<void(void)> on_audio_testing_queue_full;
};
```

**`std::function` 是什么？**

它是 C++11 引入的**函数包装器**，可以存储：
- 普通函数指针
- Lambda 表达式
- 类成员函数
- 仿函数（重载了 `()` 的对象）

简单说，它就是一个"能装各种可调用对象的盒子"。

#### 2. 设置回调（在 application.cc 中）

```cpp
// application.cc:76-86
AudioServiceCallbacks callbacks;  // 创建回调结构体

// 回调1：发送队列有数据时
callbacks.on_send_queue_available = [this]() {
    xEventGroupSetBits(event_group_, MAIN_EVENT_SEND_AUDIO);
};

// 回调2：检测到唤醒词时（带参数）
callbacks.on_wake_word_detected = [this](const std::string& wake_word) {
    xEventGroupSetBits(event_group_, MAIN_EVENT_WAKE_WORD_DETECTED);
};

// 回调3：语音检测状态变化时（带参数）
callbacks.on_vad_change = [this](bool speaking) {
    xEventGroupSetBits(event_group_, MAIN_EVENT_VAD_CHANGE);
};

// 把回调设置给 AudioService
audio_service_.SetCallbacks(callbacks);
```

**Lambda 表达式语法详解**：

```
[capture] (parameters) -> return_type { body }
   │          │              │            │
   │          │              │            └── 函数体（真正要执行的代码）
   │          │              └── 返回类型（通常可以省略，编译器自动推导）
   │          └── 参数列表（和普通函数一样）
   └── 捕获列表（从外部作用域捕获变量）
```

| 捕获方式 | 含义                 | 示例                     |
| -------- | -------------------- | ------------------------ |
| `[this]` | 捕获当前对象指针     | 可以访问类成员变量和方法 |
| `[&]`    | 引用捕获所有外部变量 | 变量改变会影响外部       |
| `[=]`    | 值捕获所有外部变量   | 变量是副本，不影响外部   |
| `[var]`  | 值捕获特定变量 var   |                          |
| `[&var]` | 引用捕获特定变量 var |                          |

在这个例子中，`[this]` 意味着 Lambda 内部可以访问 `Application` 类的成员，比如 `event_group_`。

#### 3. 触发回调（在 audio_service.cc 中）

当 AudioService 内部发生特定事件时，会检查并调用回调：

```cpp
// audio_service.cc:720-724 - 唤醒词检测到
wake_word_->OnWakeWordDetected([this](const std::string& wake_word) {
    // 先检查回调是否被设置（避免空指针调用）
    if (callbacks_.on_wake_word_detected) {
        // 调用回调，传递唤醒词参数
        callbacks_.on_wake_word_detected(wake_word);
    }
});

// audio_service.cc:107-109 - VAD状态变化
if (callbacks_.on_vad_change) {
    callbacks_.on_vad_change(speaking);
}

// audio_service.cc:426-428 - 发送队列有数据
if (callbacks_.on_send_queue_available) {
    callbacks_.on_send_queue_available();
}
```

**为什么要检查 `if (callbacks_.xxx)`？**

因为 `std::function` 默认是空的，如果直接调用空的 `std::function` 会抛出异常。检查可以确保只有设置了回调才执行。

```
   ▼
2. Application::Initialize() 执行
   │
   ├── 创建 AudioServiceCallbacks 结构体
   │
   ├── 设置 callbacks.on_wake_word_detected = [this](...) {...}
   │   └── 这里只是把 Lambda 存起来，还没执行！
   │
   └── audio_service_.SetCallbacks(callbacks)
       └── AudioService 把 callbacks 保存到成员变量 callbacks_

3. 用户说出"小智小智"（唤醒词）
   │
   ▼
4. AudioService 内部的 WakeWord 模块检测到唤醒词
   │
   └── wake_word_->OnWakeWordDetected(...) 被调用

5. AudioService 触发回调
   │
   └── callbacks_.on_wake_word_detected("小智小智")
       │
       ▼
6. Lambda 函数真正执行！
   │
   └── xEventGroupSetBits(event_group_, MAIN_EVENT_WAKE_WORD_DETECTED)
       │
       ▼
7. Application 的主事件循环检测到事件
   │
   └── HandleWakeWordDetectedEvent() 被调用
       │
       ▼
8. 设备开始听用户说话...
```

## 第四步：对比传统方式，理解 Lambda 的优势

### 传统方式（C 风格回调）

```cpp
// 1. 定义回调函数
void onWakeWordDetected(void* arg, const char* wake_word) {
    Application* app = (Application*)arg;
    app->HandleWakeWord(wake_word);
}

// 2. 设置回调时需要传递 this 指针
audio_service_.SetWakeWordCallback(onWakeWordDetected, this);
```

**缺点**：
- 需要额外定义全局函数或静态函数
- 需要手动传递 `this` 指针（`void* arg`）
- 类型不安全（`void*` 强制转换）
- 代码分散，不易阅读

### Lambda 方式

```cpp
callbacks.on_wake_word_detected = [this](const std::string& wake_word) {
    xEventGroupSetBits(event_group_, MAIN_EVENT_WAKE_WORD_DETECTED);
};
```

**优势**：
- **代码内联**：回调逻辑就在设置的地方，一目了然
- **自动捕获**：`[this]` 自动捕获当前对象，无需手动传递
- **类型安全**：参数类型明确，无需强制转换
- **灵活性**：可以捕获任意外部变量

## 第五步：另一个经典案例——定时器回调

项目中还有一个更特殊的 Lambda 用法，用于 C 风格 API：

```cpp
// application.cc:36-46
esp_timer_create_args_t clock_timer_args = {
    .callback = [](void* arg) {
        // 这是一个不带 this 的 Lambda！
        Application* app = (Application*)arg;
        app->event_group_;  // 现在可以访问了
    },
    .arg = this,  // 通过 C API 的 arg 参数传递 this
    .name = "clock_timer",
};
```

**为什么不能直接用 `[this]`？**

因为 `esp_timer_create_args_t` 是 C 语言结构体，它的 `callback` 字段类型是：
```cpp
void (*callback)(void* arg);  // C 风格函数指针
```

C 语言不认识 Lambda，所以必须用不带捕获的 Lambda `[]()`，然后通过 `void* arg` 手动传递 `this`。

## 总结

| 概念                | 解释                                       |
| ------------------- | ------------------------------------------ |
| **Lambda**          | 匿名函数，可以捕获外部变量，代码内联       |
| **std::function**   | 函数包装器，存储各种可调用对象             |
| **回调**            | 当某个事件发生时，调用预先设置的函数       |
| **[this]**          | 捕获当前对象指针，让 Lambda 可以访问类成员 |
| **`if (callback)`** | 检查回调是否为空，避免异常                 |

这个项目中的回调模式非常典型：**一个模块（AudioService）提供回调接口，另一个模块（Application）注册回调函数，当事件发生时自动通知**。这种模式在 GUI 编程、网络编程、嵌入式开发中都非常常见！
